# RCA — pedana-lookup: orders registered on the site do not appear in the Android app

## Summary
The Android APK and the backend↔database wiring are **both correct**. The real problem is that **no order-creation write has reached the production database since the first-deploy migration on 2026-11-13**. The orders the user believes are being registered are not landing in production — they are either being registered against the **preview** site (which, as noted, does not sync) or are **failing auth (401)** against production.

## Evidence

### 1) The Android APK — backend URL and code version (user question 1)
- Latest Android build run `dbu83na4hkhs73c2pjcg` (EAS build `2cdfff17-8c53-4e1a-8909-405bc683de5c`), created **2026-11-17 16:33**.
- `android_prepare` log: **"Using code version: d5ac8d2c-6ce7-4ec9-9510-781a89ba69b1"** — this is the deploy of 2026-11-17 16:25, i.e. **≥ b1b3c5d5** (b1b3c5d5 was 15:28). So the APK **does** contain the newest "Magazzino filters to dataArrivo==today by default" feature.
- Backend URL: `frontend/.env` ships `EXPO_PUBLIC_BACKEND_URL=https://pedana-lookup.preview.emergentagent.com`; the EAS build's `sed` rewrites the preview URL to the production backend. The production backend URL (`REACT_APP_BACKEND_URL`) is verified = **https://pedana-lookup.emergent.host**. ⇒ The APK is built pointing at **production**, not preview.
- The APK is one deploy behind the current live backend (`357a6127`, deployed 19:30), but that is immaterial to this issue.
- **Conclusion: the APK is not the cause.**

### 2) Production DB `pedane` (user question 2)
- DB bound to the live backend: `pedana-lookup-test_database` (verified: `DB_NAME` secret matches, `MONGO_URL` is the Atlas secret, `server.py` line 25 `load_dotenv(ROOT_DIR/'.env')` uses default `override=False` so K8s secrets win over the baked `backend/.env` which still has `mongodb://localhost:27017` / `test_database`). - `distinct(dataArrivo)` = **0** → none of the 558 migrated docs even have a `dataArrivo` field.
- **No `pedane` document has been inserted since 2026-11-13** — i.e. the collection is exactly the first-deploy migration snapshot. `POST /api/pedane` and `POST /api/import-pdf` both stamp `createdAt` on insert, so new orders would be visible if they existed.

### 3) Production backend logs, last 24h (user question 3)
- Backend is live and healthy (uvicorn on :8001).
- `GET /api/sito` → 200 (office page loads), `GET /api/riepilogo?data=2026-11-18` / `?data=2026-11-17` → 200 (authenticated ufficio reads succeed — `riepilogo` requires `require_ufficio`).
- **The only write attempt, `POST /api/import-pdf`, returned 401 Unauthorized.**
- **No `POST /api/pedane` reached this backend at all**, and **no `GET /api/pedane/tutte`** either.
- Auth model is Bearer-token (`Authorization: Bearer …` → `sessions` collection), not cookies — so this is not a cookie-domain/secure-flag production quirk.

## Root cause
Order-creation writes are **not reaching the production backend/DB**. Reads (`riepilogo`, `sito`) from an authenticated ufficio session do reach production and succeed, but zero successful creates have occurred since Nov 13. Combined with the user's own note that some registrations are done on the preview site, the strong inference is that the "missing" orders were registered against **preview** (no sync), and/or the production create path is failing auth (the observed `POST /api/import-pdf` → 401). Either way, production has nothing new to serve, so the app correctly shows nothing.

## Secondary (display) factor — matches the user's note
Even the 558 migrated docs have **no `dataArrivo`**, so the newest app's default "Magazzino = dataArrivo==today" filter hides them; they only appear via **'Tutte'** or search. This is consistent with the user's note but is NOT the cause of the missing-orders complaint.

## Not a deploy/platform/APK fault
- APK build: success, correct code version, correct production backend URL.
- Backend↔DB binding: correct and verified.
- No source bug was reproducible in the sandbox (the write failure is auth/credential-dependent and the sandbox has no live creds/session).
